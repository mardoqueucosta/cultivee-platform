## Decisoes de design

### v4.1.51 — Detector de incidentes (worker)

Bug latente desde o deploy inicial do Worker. Condicao era:
```js
if (wasHealthy && !result.healthy && fail_streak >= INCIDENT_OPEN_THRESHOLD)
```
- 1o check de falha: `wasHealthy=true` mas `fail_streak=1` (< 2 threshold)
- 2o check de falha: `fail_streak=2` mas `wasHealthy=false` (prev.healthy
  ja virou false no ciclo anterior)

Resultado: o `wasHealthy && fail_streak >= 2` NUNCA era true ao mesmo tempo.

Fix: detectar TRANSICAO via `prevFails < THRESHOLD && new_streak >= THRESHOLD`.
Independe do flag `healthy` anterior. Mesma logica espelhada pra closeIncident.

Honestidade UX: adicionei nota azul info na pagina `status.cultivee.com.br`
informando que quedas anteriores ao fix podem nao constar (auto-desativa
30 dias depois — gap histórico naturalmente sai da janela).

### v4.1.52 — Per-module vs global

User explicitou a filosofia: "modulos sao entidades INDEPENDENTES, interface
e router/storage, nao tem infra de decisao sobre os modulos". Refator alinha:

| Antes (v4.1.41) | Depois (v4.1.52) |
|---|---|
| `ALERT_CATALOG` global (6 alertas) | `UNIVERSAL_ALERTS` (4) + `PRODUCT_ALERTS[type]` (variavel) |
| `user_alert_prefs (user, type)` | `module_alert_prefs (user, chip, type)` |
| `GET /api/profile/alerts/catalog` | `GET /api/modules/<chip>/alerts/catalog` |
| `PUT /api/profile/alert-prefs/<type>` | `PUT /api/modules/<chip>/alert-prefs/<type>` |
| Cache singleton `_notifCardCache` | `_notifCardCacheByChip[chipId]` |
| Janela silencio replicada em N cards | UM modal no menu do user |

User aprovou drop direto da `user_alert_prefs` (era beta — sem migracao).
Endpoints antigos REMOVIDOS sem alias (sem 1-2 release de transicao). Risco
calculado e validado: nenhum cliente externo conhecido.

### v4.1.57 — Historico per-module + harmonia visual

User apontou: card mostrava alertas de OUTROS modulos no historico. Em
um card per-module isso confundia. Decisao: filtrar por chip_id +
adicionar tabs (7d/30d/60d) + stats agregados pra alinhar visualmente
com o modal "Historico de conexao" (v4.1.31, ja per-module).

Endpoint global `/api/profile/alerts/history` mantido por 1 release
(removido em v4.1.58 apos auditoria — ninguem chamava).

### v4.1.58 — Alertas Hidro-Farm (server-only)

Por que server-only: campos `temperature`, `humidity`, `dht_valid`,
`valve_entrada`, `level_high` ja eram reportados pelo firmware desde
v4.0.x. Adicionar alerta = adicionar `_check_*` no `notifications.py`,
zero firmware change. Velocidade > completude.

Helper `_dht_threshold_check` generico encapsula o pattern timer
(timestamp persistido em `ctrl_data`, sobrevive a restart, dispara
apos N seg de condicao continua, limpa quando volta ao normal).
Reusado pelos 3 checks de DHT — evita duplicacao.

`reservoir_fill_stuck` so ativa em `valve_auto=true` (modo manual e
responsabilidade do user — alertar nesse caso seria spam).

### v4.1.59 — Alertas Cam (firmware + server)

`cam_init_failed`: simples — variavel global `camInitErrorCode` setada
no `initCamera()` se `esp_camera_init` falhar. Reportada no JSON.

`cam_dark_frame`: deteccao de "frame anormal" via tamanho do JPEG
(proxy de complexidade visual). Considerei multiplas abordagens:
1. **fmt2rgb888** + calculo de luminancia real → custoso (UXGA = 5.7MB),
   altera fluxo de captura
2. **Capturar GRAYSCALE separado** pra brilho → reinit camera, arrisca
   quebrar captura principal
3. **Amostra de bytes do JPEG raw** → proxy fraco, JPEG nao tem mapeamento
   linear pra brilho
4. **Tamanho do JPEG** → frame escuro/uniforme/tampado → JPEG MUITO menor
   que baseline (poucos detalhes pra comprimir)

Escolhi #4 — pragmatica, server-only, baseline rolling window de 10
capturas, alerta se ultimas 5 < 30% da mediana. Documentado como
heuristica de "frame anormal" (nao luminancia real). Cobre os casos
reais que importam: lente tampada, escuridao total, falha de sensor.

### v4.1.60 — Email contextualizado

Antes: `Cultivee Alerta - [P1] Reservatorio nao enche` — qual modulo?
Inbox confusa. Nome aparecia embutido na 1a frase do body, sem destaque.

Depois: `Cultivee · Controle Hidro 7000 · Reservatorio nao enche [P1]`.
Body comeca com bloco metadados (Modulo / Severidade / Hora) pra scan
rapido. Footer educativo aponta as 2 acoes possiveis (canal per-modulo
ou silencio global).

Bonus: filter Gmail por modulo agora funciona
(`subject:"Hidro 7000"`). Antes impossivel sem ler corpo.

## Bugs encontrados + licoes (reforcadas ou novas)

### Bug 1 — `sqlite3.Row` nao tem `.get()` (REPETIDO da v4.1.0)

**Sintoma**: card de notificacoes mostrava
`Erro: Unexpected token '<', '<!doctype "... is not valid JSON`. Endpoint
retornava HTML (pagina de erro 500) que o frontend tentava parsear como JSON.

**Trace**:
```
File "/app/app.py", line 636, in module_alerts_catalog
AttributeError: 'sqlite3.Row' object has no attribute 'get'
```

**Causa**: `request.user` vem de `get_user_by_id` que retorna `sqlite3.Row`
(NAO `dict`). `.get()` nao existe em Row.

**Ja existia bug latente** em `module_notification_prefs` (linha 593) com
o mesmo padrao — nunca foi exercitado por admin, nunca crashou. Corrigido
de carona.

**Fix**: helper `_row_field(row, field, default=None)` em `app.py` que
encapsula `try: row[field] except (IndexError, KeyError, TypeError):
return default`. Funciona pra Row E pra dict.

**Licao reforcada (3a vez)**: funcoes `models/get_*` retornam tipos diferentes:
- `get_user_by_id` -> `sqlite3.Row`
- `get_module_by_chip_id` -> `dict` (`return dict(module) if module else None`)
- Outros: variavel — checar antes de usar `.get()`

**Quando em duvida**: `_row_field(row, field, default)`.

### Bug 2 — `const` reassignment em strict mode

**Sintoma**: historico mostrava `Erro: Assignment to constant variable`.

**Causa**: `_notifHistoryCache` declarado `const`, mas em `loadCardHistory`:
```js
_notifHistoryCache = { ts: now, alerts: ... };  // BUG
```

**Fix**: mutar propriedades em vez de reatribuir:
```js
_notifHistoryCache.ts = now;
_notifHistoryCache.alerts = resp.alerts || [];
```

**Licao**: `const` impede REATRIBUICAO da referencia, nao MUTACAO do
conteudo. Em strict mode (modo padrao do JS moderno), reatribuir lanca
TypeError. Pra cache global como `const obj = {ts:0,...}`, todos os
updates devem ser `obj.prop = ...`, nunca `obj = {...}`.

### Bug 3 — `<details>` perde estado entre re-renders

**Sintoma**: clicar em "HISTORICO (30 DIAS)" abria, mas fechava ~5s depois
(no proximo poll do dashboard).

**Causa**: `loadCtrlStatus` polla a cada poll do ESP32 e `_lastCtrlKey`
inclui `temperature/humidity` (DHT11 muda toda leitura). Sempre que a temp
varia, `renderDashboard` reescreve `container.innerHTML` inteiro — o
`<details>` e recriado com estado default (fechado). Estado open/closed
e DOM transient state, nao vem do servidor nem do cache.

**Fix**: persistir estado em `localStorage` com chave per-chip
(`notif-history-open-<chipId>`). 2 helpers `_isHistoryOpen` /
`_setHistoryOpen` + `ontoggle` no `<details>`.

**Licao**: qualquer estado UI transient (open/closed, scroll position,
selected tab) sobre componentes dentro de containers re-renderizados a
cada poll PRECISA ser persistido (localStorage por padrao). Mesma raiz
do flash visual que ja foi corrigido no v4.1.50 — mas pra estado de
componente.

### Bug 4 — Cache desatualizado revertia checkbox

**Sintoma**: clicar checkbox push/email fazia o estado mudar visualmente,
mas se o card fosse re-renderizado dentro de 60s, voltava pro estado
antigo. PUT pro servidor funcionava — bug so visual.

**Causa**: `saveCardAlertPref` salvava no servidor mas NAO atualizava o
cache local. Cache `_notifCardCache` ficava com valor antigo por TTL de
60s. Renderizacao subsequente usava cache antigo.

**Fix**: apos PUT bem-sucedido, atualizar `_notifCardCacheByChip[chipId]`
.catalog.catalog inline (find item + mutar enabled_push/email).

**Licao**: cache de leitura precisa ser invalidado/atualizado em escritas.
Caso contrario, write-through gera inconsistencia visual ate o TTL expirar.
Solucoes: (a) invalidate + re-fetch (latencia); (b) optimistic update no
cache (escolhido). YAGNI, escolher (b).

### Bug 5 — `compile-cam.sh` PORT hardcoded

**Sintoma**: `compile-cam.sh upload` tentou COM7, mas Cam estava em COM8.

**Fix**: `PORT="${PORT:-COM7}"` aceita override via env var, mantem default.

**Licao**: scripts de gravacao de firmware DEVEM aceitar `PORT` via env.
Convencao do `compile.sh` desde v4.1.34. `compile-cam.sh` ficou pra tras.
`compile-hidrofarm.sh` provavelmente tambem (verificar quando precisar).

### Bug 6 — `sqlite3` nao existe no container `python:3.10-slim`

**Sintoma**: meu loop de validacao via SSH usou `docker exec ... sqlite3 ...`
e todos os 24 checks falharam silenciosamente com
`exec: "sqlite3": executable file not found`.

**Fix**: usar `docker exec ... python3 -c "import sqlite3; ..."` direto
(sqlite3 e um modulo Python, nao precisa do CLI).

**Licao operacional**: pra debug interativo do banco em prod, usar Python
inline (vem com a imagem) ou copiar `cultivee.db` pra /tmp do host. CLI
sqlite3 nao foi instalado no Dockerfile.

## O que foi DESCARTADO (alternativas avaliadas)

### Override per-modulo on top de global (catalog filtrado)

**Proposta inicial:** catalogo global com campo `applicable_to: ["hidro",
"hidro-farm"]`, frontend filtra. Defaults globais por user, override
opcional por modulo se user pedir.

**Por que descartado:** contradiz a filosofia "modulos sao independentes".
Introduz "decisao cruzada" (servidor decide o que mostrar baseado na
union das capabilities dos modulos do user). Substituido por solucao
totalmente per-module — mais alinhado, mais simples logo de cara.

### View "todos os alertas" no menu user

**Proposta:** modal global agregando alertas de TODOS os modulos do user.

**Por que descartado:** YAGNI. Endpoint `/api/profile/alerts/history`
inicialmente mantido pra suportar isso, depois removido (auditoria
mostrou: ninguem chamava). Recriacao trivial se demanda surgir.

### `notification_email` per-modulo

**Proposta:** "alerta da Cam vai pro email da vizinha que cuida da casa"
ou "alerta do cliente X vai pro email dele" (cenario comercial).

**Por que descartado:** YAGNI. Demanda nao apareceu. Quando aparecer,
mexer schema + UI + logica de envio.

### Decode REAL de luminancia pra `cam_dark_frame`

**Proposta:** `fmt2rgb888()` ou `esp_jpg_decode()` no firmware da Cam
pra calcular luminancia real do frame.

**Por que descartado:** RGB buffer pra UXGA = 5.7MB (nao cabe). Sub-amostragem
funciona mas complexa, arrisca quebrar captura principal. Tamanho do JPEG
e proxy honesto e suficiente pros casos reais (tampada, escuridao).

### HTML rich body em emails

**Proposta:** template HTML bonito com tabela de metadados, link visual.

**Por que descartado:** texto puro evita problemas com clientes de email
que bloqueiam HTML, mantem compat com cliente leve de IoT/celular antigo.
Email continua acionavel sem render rich.

## Roll-out de firmware (rodada final)

`v4.1.60` sync nos 4 chips em ~10min compile + ~30s OTA:

```bash
# 1. sync-version.sh --write -> products/*.h pra v4.1.60
# 2. config.h aponta hidro.h
bash compile.sh                     # 1.24 MB
# SSH single-session subindo .bin pros 2 chips Hidro
SHA=$(sha256sum build/firmware.ino.bin | awk '{print $1}')
base64 -w0 build/firmware.ino.bin | ssh ... "
  TMP=\$(mktemp); base64 -d > \$TMP
  for CHIP in E04730A7DBCC 50B525077000; do
    cp \$TMP \$FW/\$CHIP.bin
    printf '%s' '$SHA' > \$FW/\$CHIP.sha256
  done
  rm \$TMP
"
# 3. config.h -> hidro-farm.h
bash compile-hidrofarm.sh           # 1.25 MB
# SSH pra chip Farm
# 4. config.h -> cam.h
bash compile-cam.sh                 # 1.28 MB
# SSH pra chip Cam
# 5. config.h volta pra hidro.h
# 6. Loop validando firmware_version=4.1.60 nos 4 chips
```

Auto-delete dos `.bin` no servidor confirmado — volume vazio apos roll-out.
Sem brownout, sem boot loop, sem regressao.

## Convencoes operacionais reforcadas

1. **OTA single-session por produto** — agrupar uploads de chips do mesmo
   tipo em UMA SSH. Evita rate limit do fail2ban.
2. **PORT via env** em todos os scripts de compile (convencao da v4.1.34).
3. **`_row_field` defensive** em qualquer endpoint que toque `request.user`
   ou outras Rows.
4. **`docker exec ... python3 -c`** pra debug do banco em prod (sqlite3
   CLI nao tem na imagem slim).
5. **`<details>` + estado UI persistido em localStorage** — qualquer
   componente dentro de container re-renderizado a cada poll precisa
   disso (nao apenas o conteudo via cache).
6. **Cache write-through**: apos PUT, atualizar cache local imediatamente
   (otimistic update) pra evitar revert visual.
7. **Refator BREAKING** = release pequena (catalogo OU endpoints OU
   frontend OU silent_hours, NAO os 4 ao mesmo tempo). Lecao reforcada
   nessa rodada — fiz tudo junto na v4.1.52, custou 3 hotfixes.
