## Fluxo da rodada (cronologico)

### 1. Pedido inicial: instalar segundo HIDRO em COM17

Usuario plugou novo ESP32 em COM17 (chip USB-Serial CH9102 — clone CH340 comum em ESP32 chineses). Pediu pra eu gravar o firmware nele.

**Sequencia tecnica**:
1. Verifiquei `firmware/config.h` — produto HIDRO + `ENV_PRODUCTION` ativo (`E04730A7DBCC` parceiro estava em prod, OK seguir o mesmo).
2. `compile.sh` tinha `PORT=COM7` hardcoded. Edit pra aceitar `PORT` via env var: `PORT="${PORT:-COM7}"` — melhoria permanente.
3. `bash sync-version.sh --write` alinhou `FIRMWARE_VERSION` ao `APP_VERSION` (4.1.31 → 4.1.33).
4. `PORT=COM17 bash compile.sh upload` — gravou v4.1.33 com sucesso.

### 2. Pergunta: vai ter conflito com o outro HIDRO?

Audit dos 10 pontos onde poderia colidir (chip_id, banco, AP SSID, mDNS, NVS, pareamento, OTA, AlertManager, PWA, container). **Conclusao**: na pratica nao colide, mas tem 1 risco — `Cultivee-Hidro` (AP SSID) e `cultivee-hidro.local` (mDNS) **conflitariam** se algum dia os 2 ficassem na mesma rede WiFi simultaneamente.

### 3. Usuario reportou: "so vejo 1 AP `Cultive-Hidro`"

Isso era esperado: HIDRO #1 estava em modo STA (conectado), nao difundia AP. So o #2 novo aparecia. Mas concordamos em **prevenir** o problema futuro adicionando sufixo MAC ao SSID/mDNS.

### 5. Operacao OTA via SSH (sem token admin)

Em vez de pedir token admin do user, fiz o OTA enviando `.bin` direto pro volume Docker via SSH. Mais rapido pra ele.

```bash
SHA=$(sha256sum build/firmware.ino.bin | awk '{print $1}')
base64 -w0 build/firmware.ino.bin | ssh ... "
  FW='/var/lib/docker/volumes/cultivee_cultivee-data/_data/firmware'
  base64 -d > \"\$FW/E04730A7DBCC.bin\"
  printf '%s' \"\$SHA\" > \"\$FW/E04730A7DBCC.sha256\"
"
```

**Cronologia confirmada nos logs**:
- `09:12:23` servidor detectou firmware pendente
- `09:12:23` ESP32 baixou (1.240.480 bytes — SHA bate)
- `09:12:23` servidor removeu `.bin` (anti-loop, fix da v4.1.8)
- `09:12:54` ESP32 reiniciou + re-registrou (~31s offline)

Sem rollback A/B disparado — firmware estavel apos 1 reboot.

### 6. v4.1.35 — Firmware reporta `firmware_version` + PWA desambigua nomes

**Pedido implicito**: como saber qual versao roda em cada modulo? Hoje so abrindo `/update` na rede local. **Fix**: adicionar `firmware_version` no JSON do register.

**Tambem nesse pedido**: a screenshot mostrava 2 cards `Controle Hidro` identicos no PWA. **Fix**: anexar sufixo `chip_id.slice(-4)` ao label fallback (`Controle Hidro · DBCC`).

**Bug 1 que cometi**: coloquei `firmware_version` na **raiz do JSON** do register. Mas o `register_module()` do server so extrai chaves especificas da raiz (chip_id, type, ip, ssid, etc.) e o resto desce pra `data.get("ctrl_data", {})` — campo nao era armazenado em lugar nenhum.

**Fix do bug**: mover pra dentro do sub-objeto `"ctrl_data":{...}` no firmware (commit `8eafe4b`). Validacao: ambos HIDROs reportando fw=4.1.35 no banco apos OTA.

**Licao**: ao adicionar campo novo no contrato firmware↔server, **validar a forma esperada no servidor primeiro** — nao apenas adicionar no firmware e esperar funcionar.

### 7. v4.1.36 — Layout fix (4o card nao estica)

Usuario reportou screenshot: ao adicionar 4o modulo (HIDRO #2 logo apos pareamento), a 2a linha do dashboard mostrava o card **esticado** ocupando 100% da largura.

**Causa**: CSS `flex: 1 1 calc(33.333% - 0.67rem)` + `flex-grow: 1`. Em linhas cheias o grow distribuia espaco; em linha incompleta com 1 item, o grow expandia pra 100%.

**Fix**: trocar Flex por **CSS Grid auto-fill** em ambos os containers (`.modules-list` na barra + `#module-content` no dashboard):
```css
display: grid;
grid-template-columns: repeat(auto-fill, minmax(NNNpx, 1fr));
```
`auto-fill` cria N colunas que cabem mesmo se vazias — items mantem largura natural alinhados a esquerda. Mobile (sem `@media`) continua flex column.

**Bug 2 que cometi (sutil)**: nao mexi no `.modules-list` na primeira tentativa de fix porque achei que era so o `#module-content`. Mas a mesma colisao acontecia na barra de selecao. Felizmente identifiquei antes do commit e arrumei os 2 juntos.

**Licao**: bug de CSS de layout responsivo geralmente afeta **ambos** os grids do mesmo padrao — verificar todos os usos do mesmo padrao CSS antes de assumir que e local.

**Implementacao**:

- **#1 Alerta proativo (backend)**: novo pacote `server/jobs/` com `offline_watcher.py` — thread daemon roda a cada 60s. Pra cada modulo pareado: se offline >= 60min e cooldown OK, dispara alerta P1 (push + email). Se >= 24h, escala P0. Se voltou apos queda longa, dispara recovery.

  - Iniciado em `app.py` apos init_db. Falha silenciosa se import quebrar.

- **#2 "Em curso · Xmin" no modal**: edit cirurgico em `_renderUptimeBody`. Antes mostrava so "<i>em curso</i>" sem tempo decorrido. Agora calcula `now - occurred_at` e mostra "OFFLINE · em curso · 45min".

- **#3 Card user com "Offline ha Xmin"**: edit em `loadInlineUptime`. Quando `s.current_status === 'offline'`, substitui "Uptime 7d: X% · sem quedas" por `🔴 Offline ha 45min` em vermelho. Visivel imediatamente sem precisar abrir modal.

**Validacao em producao**:

Thread detectou no PRIMEIRO ciclo, push entregue pra 7 endpoints + email pro `mardo.abc@gmail.com`. **Lock funcionou** (alert_log tem APENAS 1 entrada apesar dos 2 workers). 8 push subs antigas (410 Gone) foram removidas automaticamente pelo handler existente — limpeza colateral.

## Descobertas operacionais (NUNCA esquecer)

### `docker compose restart` nao re-le `env_file`

Sintoma: adicionei `PLATFORM_INCIDENT_SECRET` no `.env`, fiz `docker compose restart app`, container voltou mas endpoint retornava 401 `webhook_disabled`.

Causa: env vars sao capturadas na **CRIACAO** do container. `restart` apenas reinicia o processo dentro do container existente, nao reaplica `env_file`.

**Solucao**: `docker compose up -d --force-recreate app` recreates o container, re-lendo `env_file` completo.

Adicionado a CLAUDE.md + memory.

### Nome do service no compose nao e `cultivee-app`

`container_name: cultivee-app` (linha 6 do `docker-compose.yml`) **mas** `services.app` (linha 2). Logo:
- `docker compose restart cultivee-app` → "no such service"
- `docker compose restart app` → funciona
- `docker restart cultivee-app` → funciona (`docker` direto usa container_name)

### API CF retorna 201 (nao 200) no primeiro PUT do secret do Worker

Meu `deploy.sh` checava `[[ "$HTTP_CODE" != "200" ]]` e falsamente imprimia "FALHOU" na primeira configuracao. Corrigi pra aceitar 200 OU 201.

- **Compilar pra outro COM**: `PORT=COMxx bash compile.sh upload`
- **Editar `.env` da VPS**: SSH single-session + `docker compose up -d --force-recreate app` (NAO `restart`)
