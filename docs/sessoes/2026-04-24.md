## Por release

### v4.1.32 — Status da plataforma no admin

**Problema**: depois da sessao anterior (status page externa em `status.cultivee.com.br`), nao havia jeito facil de o admin ver "está tudo OK?" sem abrir outra aba. Tambem, quando o servidor caia, todos os modulos pareciam offline e o admin nao sabia que a culpa era do servidor.

**Decisoes de arquitetura**:

1. **Frontend consome o CF Worker direto, sem proxy pela VPS** — mais rapido, sem carga extra, e principalmente: nao depende da VPS pra ver se a VPS caiu.
2. **Cruzamento modo A** (aviso no modal de uptime) em vez de B (timeline visual) ou C (marcar backend retroativamente). A entrega 90% do valor com 25min de trabalho. C ficou pra proxima rodada.
3. **Card no topo** do admin em vez de aba separada — padrao Grafana/Sentry/Datadog, admin ve na hora que entra.

**Arquivos principais**:
- `server/static/app.js` — `loadAdminPlatformStatus`, `_fetchPlatformStatus` (cache 60s), `_renderServerIncidentsOverlap`
- `server/templates/index.html` — `#admin-platform-card` novo
- `server/app.py` — CSP libera `connect-src https://status.cultivee.com.br`
- `monitoring/cf-worker/uptime.js` — `/check` retorna snapshot consolidado, `Access-Control-Allow-Origin: *`, `Cache-Control: public, max-age=30`
- `monitoring/cf-worker/uptime.js` — footer sem link JSON (B2C nao precisa)

### Fix custo KV (dentro da v4.1.32)

**O que aconteceu**: email Cloudflare as 10:30 UTC do dia 24 — "Daily request limit exceeded for Cloudflare Workers KV free tier (1k/dia)".

**Minha estimativa original estava errada**. No README inicial eu havia escrito "~720 writes/dia" mas cada check fazia 2 writes por componente (`current:` + `daily:`). Com cron `*/2` × 2 componentes × 2 writes = **2.880 writes/dia**, 2,88× o limite.

**Duas correcoes combinadas**:

1. **Acumulador diario in-place dentro do `current:{id}`** — novos campos `day`, `today_checks`, `today_healthy`, `today_total_latency_ms`, `today_max_latency_ms`. `daily:{YYYY-MM-DD}` passa a ser escrito 1x por dia por componente, so na virada do dia. `getDailySeries` materializa o dia atual direto do `current:` (sem I/O extra).

2. **Cron `*/2` → `*/5`** — detecao 5min em vez de 2min, padrao Uptime Robot free.

**Resultado**: ~578 writes/dia (58% do limite), folga de 42%. TTL do `current:` subiu de 24h pra 7d (acumulador precisa sobreviver a pausas do cron).

### v4.1.33 — Cruzamento retroativo (opcao C2 que havia sido rejeitada antes)

**Problema herdado da v4.1.32**: mesmo com o aviso laranja no modal, o evento offline do modulo continuava sendo contado no `uptime_pct`. Pra um SLA futuro, isso e critico — nao da pra cobrar SLA do modulo quando a queda foi da plataforma.

**Solucao escolhida (C2 completa)**:

1. CF Worker posta webhook HMAC pra VPS em `openIncident`/`closeIncident`.
2. VPS valida (HMAC-SHA256 + anti-replay 5min), faz upsert em `platform_incidents`, e UPDATE retroativo em `module_status_events` marcando `reason='server_down'`.
3. `get_module_uptime_summary` passa a filtrar `server_down` do calculo (default `exclude_server_down=True`).
4. Frontend ganha badge cinza "SERVIDOR" nos eventos marcados + aviso azul no topo do modal.

**Arquivos principais**:
- `server/models/db.py` — tabela `platform_incidents` nova (idempotente por `webhook_id`).
- `server/models/modules.py` — `upsert_platform_incident`, `mark_module_events_as_server_down`, refactor de `get_module_uptime_summary` (retorna `uptime_pct` filtrado + `uptime_pct_raw` bruto).
- `server/models/__init__.py` — re-exporta os helpers novos.
- `server/app.py` — `POST /api/platform-incident` com HMAC-SHA256 + timestamp anti-replay.
- `monitoring/cf-worker/uptime.js` — `postIncidentToVPS(incident)`, `hmacSha256Hex` via `crypto.subtle` (Workers nao tem `crypto.createHmac` do Node).
- `monitoring/cf-worker/deploy.sh` — secao 3 de secret provisioning via API CF.
- `server/static/app.js` — render dos eventos ganha badge cinza + aviso azul de exclusao.

**Autenticacao do webhook**:
- Secret `PLATFORM_INCIDENT_SECRET` (64 hex chars) compartilhado.
- HMAC-SHA256 sobre `{timestamp}.{body}` (timestamp dentro do body — anti-replay).
- Janela aceitavel: ±5min (drift CF edge ↔ VPS).
- `hmac.compare_digest` pra evitar timing attacks.
- Silenciosamente desativado (401 `webhook_disabled`) se secret nao estiver no env.

## Incidente de seguranca (minor)

### O que aconteceu

Pra diagnosticar por que o endpoint rejeitava webhook com `webhook_disabled` apos o primeiro restart, rodei:

```bash
docker exec cultivee-app sh -c 'echo "has_secret: ${PLATFORM_INCIDENT_SECRET:+YES}${PLATFORM_INCIDENT_SECRET:-NO}"'
```

A intencao era imprimir "YES" ou "NO". Mas eu errei a sintaxe:
- `${VAR:+YES}` — se setada, retorna "YES". OK.
- `${VAR:-NO}` — se setada, retorna **o valor**, nao "NO". Errado.

Com a variavel populada, o output foi `has_secret: YES<secret>`. O secret vazou no terminal e foi capturado no log da conversa.

### Remediacao imediata

1. Gerei secret novo (`secrets.token_hex(32)`).
2. SSH single-session na VPS: removi linha antiga do `.env`, adicionei nova, `docker compose up -d --force-recreate app` (descoberta: `restart` nao re-le `env_file`).
3. `bash monitoring/cf-worker/deploy.sh` atualizou o secret do Worker via API CF.
4. Verificacao end-to-end com HMAC valido: POST 200 OK.
5. Apaguei o arquivo tmp local.

### Licao aprendida

Nunca mais usar `${VAR:-}` pra check de presenca de secret. Usar:
- `${#VAR}` — so comprimento
- `[ -n "$VAR" ] && echo YES || echo NO` — booleano explicito
- Ou fazer check do lado de fora do shell remoto (via retorno HTTP do proprio endpoint).

## Descobertas operacionais

### `docker compose restart` nao re-le `env_file`

Apos adicionar nova linha no `.env`, o primeiro `docker compose restart app` nao propagou a nova env var pro container. Porque `restart` apenas envia SIGTERM/SIGKILL + start — as env vars foram capturadas na CRIACAO do container.

**Solucao**: `docker compose up -d --force-recreate <service>` recreates o container, re-lendo o `env_file` completo.

Documentado em CLAUDE.md + memoria persistente pra proximas rotacoes de secret.

### Nome do service no compose nao e `cultivee-app`

`container_name: cultivee-app` mas `services.app`. Tentei `docker compose restart cultivee-app` e deu "no such service". Comando correto: `docker compose restart app`.

### API CF retorna 201 no primeiro PUT do secret (nao 200)

Meu `deploy.sh` checava `[[ "$HTTP_CODE" != "200" ]]` e falsamente imprimia "FALHOU" na primeira configuracao do secret. Cosmetico — o secret foi criado mesmo assim (`success: true` no body). Corrigido pra aceitar 200 OU 201.

## Convencoes operacionais critacas (recap)

- **SSH VPS**: uma sessao por vez (fail2ban). Encadear comandos com `&&`.
- **Rotacao de secret**: requer `docker compose up -d --force-recreate app`, NAO `restart`.
- **Tokens/secrets**: sempre em `.env` da VPS ou env secret do Worker (API CF), nunca no repo.
- **APP_VERSION**: fonte unica em `server/config.py`. Nao esquecer de bump junto com mudancas visuais (SW cache invalida automaticamente).
- **Para diagnosticar env vars de container**: NUNCA usar `${VAR:-}`, usar `${#VAR}` ou validacao booleana explicita.
